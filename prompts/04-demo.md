# Stage 4 — Demo 视频与 Slides

> 这是当前阶段的完整工作说明。开始前先读 `STATE.md`；完成后把证据写入 `evidence/`，更新 `STATE.md`，再读下一个阶段文件。不要提前执行后续阶段。
>
> 开始前先加载 `demo-recorder` skill；scene 规范、渲染命令和抽帧验收以技能为准。

你同时担任专业 Presentation Designer、信息可视化设计师、Motion Graphics Designer 和技术内容导演。

目标：让 Demo Video 中的 Slides 不再只是标题、几行文字和普通背景，而是能够通过精心设计的视觉元素，帮助观众直观理解产品的技术原理、工作流程、架构及竞争优势。

### 1. 主动探索设计工具

如果环境中存在 `~/tools/demo-recorder`，先检查其中已有的全部相关工具、插件、示例及功能。

特别关注：

- Figma 及其可用插件、设计组件和导出功能
- Slides / Presentation 制作工具
- SVG、图标、矢量图形与图表生成能力
- Flowchart、Diagram、Timeline、Architecture Diagram 等信息可视化工具
- 动画、镜头缩放、平移、图层组合和转场功能
- PNG / SVG 素材导入及视频合成功能

不要假设这些功能一定可用，应实际检查工具能力。

优先复用已有插件与设计工具，不要在现有工具足够的情况下自行开发重复功能。

### 2. 从文字叙述转变为视觉解释

分析完整 Storyboard，找出适合使用视觉化表达的内容。

根据内容自主选择最合适的表现方式：

- **Flowchart**：解释用户操作流程、自动化流程和系统决策逻辑。
- **Architecture Diagram**：展示系统组件、数据流、模型、API 和后端服务之间的关系。
- **Sequence Diagram**：展示多个组件之间的交互顺序。
- **Before / After**：对比产品使用前后的操作、结果或体验。
- **Comparison Matrix**：对比现有解决方案和我们产品的差异。
- **Timeline**：展示任务执行过程、事件顺序或关键阶段。
- **Annotated Screenshot**：在真实软件截图上标注关键功能。
- **Data Visualization**：通过有意义的图表展示测试结果、性能和准确性。
- **Concept Illustration**：对抽象概念进行直观解释。
- **Step-by-Step Animation**：将复杂操作拆分成容易理解的连续步骤。

这些只是可选形式，不是必须全部使用。

每一页都应根据它需要传达的内容自主决定视觉结构。

不要机械地将所有内容制作成相同的模板。

### 3. 禁止低价值的文字 Slides

避免以下设计：

- 整页只有一个标题和三个简单关键词。
- 将完整旁白直接复制到 Slides。
- 大段文字配上毫无意义的图标。
- 所有页面都使用完全相同的布局。
- 用复杂渐变、发光效果或装饰代替实际信息。
- 明明可以用流程图说明，却只放几句话。
- 为了减少工作量而默认选择最简单的文字展示。

但是，不要为了避免简单而刻意把每一页复杂化。

在需要强调重要结论、制造停顿或引导注意力时，简洁的标题页仍然是合理选择。

核心要求不是每一页都必须复杂，而是每一页都必须有明确的视觉表达目的。

### 4. 专业视觉设计

**Visual Hierarchy**

- 让观众第一眼知道应该看哪里。
- 使用字号、对比度、布局和空间关系建立清晰的视觉层次。

**Consistency**

- 保持统一的字体、配色、图标风格、线条和组件。
- 根据产品本身的视觉语言建立 Presentation Design System。

**Readability**

- 视频以 16:9 横屏为默认画布，除非比赛另有规定。
- 所有文字、箭头、节点和注释在实际视频观看尺寸下必须清晰。
- 不要把大型复杂图表强行压缩到一页。

**Information Density**

- 每页应承载有意义的信息。
- 避免过度空洞，也避免信息堆积。
- 对复杂技术内容，优先拆分成多个连续画面。

**Aesthetics**

- 可以适当使用视觉深度、图层、插画、图标、连接线和强调色。
- 设计应服务于产品主题。
- 不必盲目模仿商业模板，也不要默认选择普通白底黑字。

### 5. 让静态 Slides 具有动态叙事能力

充分利用 demo-recorder 的镜头控制及动画能力。

例如，对于复杂 Flowchart：

1. 先展示整体工作流程。
2. 放大当前正在解释的节点。
3. 通过高亮、连线或箭头引导观众理解数据流向。
4. 将镜头移动到下一个节点。
5. 在关键阶段展示真实软件操作或输出。
6. 最后回到完整流程图，帮助观众建立整体理解。

如果工具支持真正的逐元素动画，可以使用逐步显现、节点高亮和连线动画。

如果只支持静态图片和镜头控制，则可以通过多张递进式 PNG、局部放大、平移及剪辑实现类似效果。

不得假装工具支持实际不存在的动画能力。

### 6. 将技术解释与真实产品演示结合

Slides 不应该取代真实 Demo。

推荐结合：

**Visual Explanation → Real Demonstration → Actual Result**

例如：

1. 先用 Architecture Diagram 解释系统如何处理输入。
2. 随后切换到真实软件，让观众看到对应流程实际运行。
3. 最后展示实际输出，并结合测试结果解释产品表现。

优先使用 Stage 3.5 中已经验证的测试数据和结果。

禁止编造性能数字、虚构测试结论或用设计效果掩盖尚未实现的功能。

### 7. 设计与导出

使用可用的 Figma、Presentation 或其他设计工具实际制作所需素材。

优先保留可编辑的设计源文件，并将素材导出为 demo-recorder 支持的格式，例如 PNG 或 SVG。

使用一致的命名规则，便于后续剪辑与修改。

对于复杂流程图，尽可能保留节点、文本、箭头和图层的独立编辑能力。

### 8. 视觉质量验收

所有 Slides 必须经过实际渲染检查。

检查：

- 文字是否清晰、是否溢出。
- 流程箭头是否指向正确方向。
- 架构图是否忠于真实系统。
- 节点、连线、标签是否重叠。
- 图表是否使用真实且正确的数据。
- 图片是否模糊或拉伸。
- 视觉风格是否一致。
- 观众能否在画面停留时间内理解内容。

如果视觉设计虽然漂亮，但无法帮助观众理解产品，必须重新设计。

### 最终要求

在制作 Demo Video 时，主动寻找可以用视觉表达替代纯文字解释的机会。

不要只是制作 PPT；要设计一套与旁白、真实操作和镜头运动相互配合的视觉叙事。

优秀的 Slides 应该让观众即使暂时关闭声音，也能理解产品的主要工作原理和价值。

最终目标：让 Demo Video 既有真实产品演示的可信度，也有专业技术介绍视频的信息表达能力。

### Stage 4 完成条件

- 视频和 Slides 已实际渲染/导出。
- 所有文字、箭头、图表清晰且使用真实数据。
- 展示的能力与 Stage 3.5 的证据一致。
- `evidence/stage-4-demo/` 包含素材、导出文件、渲染截图/检查记录。
