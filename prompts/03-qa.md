# Stage 3 — QA

> 这是当前阶段的完整工作说明。开始前先读 `STATE.md`；完成后把证据写入 `evidence/`，更新 `STATE.md`，再读下一个阶段文件。不要提前执行后续阶段。
>
> 开始前先加载 `playwright-qa` skill；runner 模板、断言和证据要求以技能为准。

你现在担任独立 QA 工程师、用户体验测试员和产品验收负责人。

目标是通过真实浏览器操作验证产品，而不是只检查代码、DOM 或单元测试。

### 测试环境

使用 Playwright 驱动无头 Firefox，优先测试实际部署的网站，同时验证本地版本。

### 第一阶段：识别用户流程

先根据产品目标识别核心用户场景，建立测试清单。

测试应覆盖：

- 首次访问与新用户使用
- 主要功能的完整端到端流程
- 所有重要按钮、表单、菜单和交互控件
- 页面导航、刷新、返回和状态保存
- 错误输入、空数据、异常状态和失败恢复
- 不同屏幕尺寸下的响应式布局
- 键盘操作及基本可访问性

### 第二阶段：实际操作

使用 Playwright 模拟用户行为。

不要只通过检查 HTML 元素是否存在来判定成功。必须真正点击、输入、提交、等待反馈，并检查最终业务状态。

重要操作至少验证：

1. 操作是否成功执行。
2. 结果是否符合预期。
3. 界面是否提供正确反馈。
4. 是否产生控制台错误、页面异常或失败请求。
5. 用户是否能够继续下一步操作。

对关键流程使用明确断言，而非仅保存截图。

### 第三阶段：视觉验证

对重要页面、交互状态和失败场景截图。

检查：

- 元素重叠、裁切、溢出和错位
- 文字可读性与视觉层级
- 按钮、表单和反馈信息是否清晰
- 桌面与移动端布局
- 加载中、空状态与错误状态
- 页面是否存在明显的视觉不一致

不要仅因为页面能够正常渲染就判定视觉设计合格。

### 第四阶段：用户体验审查

扮演第一次接触产品的真实用户。

尝试不依赖开发文档完成主要任务。

观察：

- 用户能否快速理解产品用途
- 功能入口是否容易找到
- 是否存在重复或不必要的步骤
- 是否需要猜测按钮的作用
- 错误提示是否足以帮助用户恢复
- 完成核心任务需要多少操作
- 界面是否有产品类型的辨识度；如果换成任何 SaaS 都成立，记录为设计问题

对于主观体验问题，给出具体观察，不要虚构真实用户满意度数据。

### 第五阶段：修复与回归

记录所有发现的问题，注明复现步骤、严重程度、截图或错误信息。

优先修复阻碍核心流程的问题，然后重新运行受影响的测试以及相关回归测试。

不能通过删除测试、削弱断言或绕开功能来使测试通过。

### 第六阶段：交付验收报告

提供：

- 已执行的测试场景
- Pass / Fail / Blocked 统计
- 关键流程截图
- 发现并修复的问题
- 尚未解决的问题
- 用户体验评价及改善建议
- 本地与线上版本的验证结果

如果工具、浏览器或环境不可用，明确记录阻碍，不得声称已经完成测试。

最终以用户是否真正完成任务作为主要验收依据，而不是测试脚本是否成功运行。

### Stage 3 完成条件

- 核心流程 P0/P1 问题修复并通过回归。
- 关键流程有明确断言和截图。
- 没有未解释的控制台错误或失败请求。
- `evidence/stage-3-qa/` 包含测试清单、结果、截图、问题列表、修复记录。
- 本地与线上版本都验证过。
