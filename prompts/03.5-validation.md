# Stage 3.5 — 真实世界验证

> 这是当前阶段的完整工作说明。开始前先读 `STATE.md`；完成后把证据写入 `evidence/`，更新 `STATE.md`，再读下一个阶段文件。不要提前执行后续阶段。

你现在担任独立测试研究员、数据集研究员、QA 工程师及产品能力评估员（Product Validation Engineer）。

你的目标不是证明产品能够正常运行，而是通过来自真实世界的外部测试素材，客观评估产品的实际能力、可靠性、准确性和局限性。

### 核心要求

主动上网搜集与当前产品类型相匹配的真实测试素材，不要只使用自己生成的简单样例，更不要为了让测试通过而刻意选择容易处理的数据。

### 第一阶段：理解产品与测试目标

首先研究当前项目的：

- 产品定位、目标用户及核心功能
- 产品宣称能够解决的问题
- 支持的输入格式、输出格式和使用限制
- 已实现的功能与尚未完成的功能
- 现有测试覆盖范围

根据产品类型自主确定需要验证的能力。

例如：

- **Cybersecurity / Vulnerability Scanner**：从公开的 CVE、NVD、GitHub Security Advisories、OWASP 测试项目或其他可信安全资料寻找真实漏洞案例。优先使用官方安全测试靶场、公开的漏洞复现样本，以及有明确授权的本地隔离环境。测试产品能否识别不同类型、严重程度及表现形式的已知漏洞。检查误报、漏报、漏洞描述、严重程度和修复建议的准确性。不得未经授权扫描真实第三方系统，也不得将公开存在漏洞的网站视为可自由测试的目标。
- **PDF Scanner / Document Analysis**：从 arXiv、政府公开资料库、大学资料库、开放文档数据集或其他合法公开来源取得真实 PDF。覆盖不同页数、文件大小、排版、语言、表格、图片、扫描件、公式和复杂布局。测试内容提取、OCR（如支持）、页面定位、分析结果和异常处理。使用能够人工核对或具有参考答案的文件评估准确性。
- **Image / Creative Tools**：搜集合法可用于测试的真实图片、设计样例或开放数据集。覆盖不同分辨率、画风、复杂度、透明背景、长宽比及边缘案例。检查处理质量、编辑能力、格式兼容性、视觉一致性与结果可用性。不要只凭视觉效果漂亮就认定功能成功。
- **Developer Tools / Code Analysis**：从 GitHub 上寻找有适当许可的真实开源项目及具有可验证结果的测试案例。覆盖不同项目规模、语言、依赖、代码风格和复杂程度。检查正确性、兼容性、误报率、执行效率以及是否破坏原有功能。

以上只是示例，不是固定测试类别。对于其他类型的产品，自主研究该领域最合适的公开测试资源和评估方式。

### 第二阶段：上网寻找真实测试素材

主动搜索互联网，寻找具有代表性、可信且合法可使用的测试数据。

优先考虑：

1. 官方或学术公开测试数据集。
2. 带有明确参考答案或 Ground Truth 的 Benchmark。
3. 真实开源项目、公共文档与真实案例。
4. 真实用户提交的公开问题样例。
5. 已知会导致同类产品失败的边缘案例。
6. 必要时补充合成数据，但必须与真实数据分开标记。

对每个数据来源记录：

- 来源名称与 URL
- 文件或案例的来源及版本
- 使用许可和访问限制
- 测试目的及预期结果
- 是否具有可靠的 Ground Truth
- 下载时间及必要的文件校验信息

不要把网上的任意内容直接当作正确答案。公开数据同样可能存在标注错误、过时信息和样本偏差。

涉及不可信文件、代码或网络内容时，使用隔离环境，不执行未知脚本，不泄漏密钥或个人数据。

### 第三阶段：设计有挑战性的测试集

不要只测试 Happy Path。

根据产品能力构建覆盖不同难度的测试集：

- **Basic**：常规、标准、预期能够成功的真实案例。
- **Intermediate**：不同来源、结构、格式或复杂程度的案例。
- **Advanced**：复杂排版、大规模输入、多重问题和非典型场景。
- **Edge Cases**：损坏文件、空输入、异常编码、边界尺寸、缺失字段等。
- **Negative Cases**：不应触发检测或不应返回肯定结果的案例。
- **Adversarial Cases**：在合法、安全、隔离的条件下，测试可能误导或破坏产品判断的输入。

根据实际功能合理分配样本，不必机械平均。

在测试前固定测试样本、预期行为及评分规则，避免看到结果后再修改标准。

如果缺少可靠参考答案，应将结果标记为待核实，而不是擅自判定成功。

### 第四阶段：实际执行产品测试

将取得的真实素材输入当前产品，尽可能使用与普通用户相同的操作路径和公开接口。

可以结合 Playwright、API 测试、命令行工具或其他适当方法完成自动化验证。

必须检查：

1. 产品是否接受并正确处理真实输入。
2. 输出是否符合实际事实或参考答案。
3. 是否出现误报、漏报、幻觉或错误解释。
4. 是否能处理复杂、异常和边缘样本。
5. 处理耗时、资源占用及失败恢复能力。
6. 结果是否真正满足目标用户的实际需求。

禁止为了让测试通过而：

- 删除失败样本。
- 在测试后擅自降低通过标准。
- 将没有 Ground Truth 的结果直接判定为正确。
- 只展示成功案例。
- 利用产品内部隐藏答案或测试标签。
- 把模型自我评价当作独立验证。

测试数据和参考答案必须与产品实际输入适当隔离，防止数据泄漏影响评估。

### 第五阶段：竞品基准测试（Benchmark）

如果存在可以合法使用且条件相近的竞争产品或开源替代方案，尝试使用相同测试样本进行比较。

对比：

- 任务成功率
- 准确性、误报率与漏报率
- 执行时间与资源消耗
- 输出质量和可用性
- 失败处理方式
- 复杂案例的表现

必须保证测试条件公平。无法公平对比时，明确说明，不要凭推测宣称优于竞争者。

如果有行业公认的 Benchmark，优先采用其官方评分方法。

### 第六阶段：失败分析与改进

对每个重要失败案例进行原因分析。

区分：

- 输入解析失败
- 算法或模型判断错误
- 业务逻辑错误
- 外部依赖问题
- 性能和资源限制
- 用户界面或交互问题
- 测试数据或参考答案本身的问题

优先修复影响核心能力、发生频率较高或风险较大的问题。

可以创建回归测试，确保修复后的产品不会再次出现相同问题。

但必须保留初始测试结果，不能用修复后的结果覆盖原始证据。

如需调试，可另建开发样本集；最终评估必须使用没有被反复针对性优化的独立测试样本。

### 第七阶段：真实能力评估报告

输出一份完整的 Real-World Validation Report，包括：

1. 产品测试目标和能力范围。
2. 所有真实测试素材的来源链接。
3. 测试集构成、样本数量和难度分布。
4. 测试环境、方法和可复现步骤。
5. 成功、失败、跳过及无法判断的案例。
6. 准确率、任务成功率或其他适当指标。
7. 典型成功案例及失败案例。
8. 与竞品的可验证比较（如适用）。
9. 已修复的问题和修复后的回归测试结果。
10. 当前产品尚不具备的能力。
11. 是否足以支撑产品的宣传和 Demo Video 中的展示。

提供机器可读的测试结果，以及必要的日志、截图和输出文件。

### 最终决策

根据测试证据，对核心产品能力给出：

- **PASS**：达到预先设定的验收标准。
- **PARTIAL**：部分能力达标，但存在明确限制。
- **FAIL**：核心能力未达到验收标准。
- **INCONCLUSIVE**：证据不足，无法可靠判断。

如果产品在真实数据上表现不佳，必须如实报告。

不要因为产品是我们自己开发的，就降低评价标准。

### 核心原则

测试不应该服务于证明成功，而应该服务于发现产品真正的能力边界。

主动寻找会让产品失败的真实案例，同时确保测试合理、合法、安全、可复现。

我们需要知道的不仅是产品能处理什么，更是它不能处理什么，以及为什么不能处理。

最终目标：确保产品在 Demo Video 中展示的能力，不只是精心挑选的理想案例，而是有真实世界测试证据支持的能力。

### Stage 3.5 完成条件

- `evidence/stage-3.5-validation/` 包含报告、测试集清单、来源、原始结果、日志/截图。
- 有明确的 PASS / PARTIAL / FAIL / INCONCLUSIVE。
- 失败案例没有被删除或掩盖。
- 原始测试结果和修复后结果分开保存。
